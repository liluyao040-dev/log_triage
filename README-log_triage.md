# log_triage —— Web 日志攻击特征批量筛查工具

> ⚠️ **诚实定位（重要）**：这是你**自主开发的自学项目**，不是护网现场的实战工具。
> 简历和面试里一律说"自主开发"，**绝对不要说"在护网中投入使用"**——一旦被追问部署细节就会崩。
> 这个项目的作用是证明你有**工程化思维**，不是证明你干过运维。

---

## 一、一句话介绍

用纯 Python 标准库写的 Web 访问日志筛查工具：把 Nginx / Apache / IIS 日志批量过一遍，自动按源 IP 聚合出攻击画像、打优先级分数、识别目录扫描与 Webshell 交互行为，并导出 JSON / CSV 报告，让值守人员不用逐条翻日志。

## 二、我为什么要做这个

护网值守和日常安全运营里，最耗人的不是"看不懂告警"，而是**告警太多、人太少**：

- 天眼 / 态势感知一天几千上万条，人眼翻日志根本翻不完
- 真正需要优先处置的可能只有几条，但你要先把噪声看完才能找到
- 值守日报需要"按源 IP 统计攻击类型"，手工统计又慢又容易错

这个工具解决的就是 **"把日志变成按优先级排好的研判队列"** 这一步。

## 三、快速开始

```bash
# 1. 生成样例日志并分析（含 8 类攻击流量，240 行，无需准备数据）
python log_triage.py --demo

# 2. 分析真实日志
python log_triage.py access.log

# 3. 只看向量最高的 20 个源 IP，且只看高危以上
python log_triage.py access.log --top 20 --min-level high

# 4. 导出报告
python log_triage.py access.log --json report.json --csv hits.csv

# 5. 白名单：把自家漏扫和内网网段排除掉（真实运营中最大的误报来源）
python log_triage.py access.log --whitelist-ip 10.0.0.0/8 --whitelist-ip 192.168.0.0/16 \
                                --whitelist-ua "my-scanner" --whitelist-ua nessus
```

**零依赖**：只用 Python 标准库，不需要 pip install 任何东西，拷到任何装了 Python 3.8+ 的机器上都能跑。

## 四、检测规则（10 类）

| 规则 ID | 名称 | 级别 | 检测依据 |
|---|---|---|---|
| SQLI | SQL 注入 | 严重 | `union select`、`sleep()`、`extractvalue()`、`information_schema`、`or 1=1`、`--` 注释等 |
| CMDI | 命令注入 | 严重 | `;cat`、`\|whoami`、`$()`、反引号、`/bin/sh`、`/dev/tcp/`、`nc -e` |
| PATH-TRAVERSAL | 路径穿越 | 严重 | `../../`、`/etc/passwd`、`win.ini`、`system32\config` |
| COMPONENT-RCE | 组件漏洞利用 | 严重 | `${jndi:ldap`（Log4j2）、`rememberMe=`（Shiro）、`@type:`（Fastjson）、`class.module.classLoader`（Spring4Shell）、`wls-wsat`（WebLogic） |
| XSS | 跨站脚本 | 高 | `<script>`、`onerror=`、`javascript:`、`document.cookie`、`eval(` |
| UPLOAD | 文件上传/脚本落地 | 高 | `filename=xxx.jsp`、URI 出现 `.jsp/.php/.ashx` 等脚本后缀 |
| SENSITIVE-PROBE | 敏感路径探测 | 高 | `.git/config`、`.env`、`/actuator/env`、`/druid`、`backup.zip`、`wp-login.php`、`/manager/html` 等 |
| SCANNER-UA | 扫描器 UA | 高 | sqlmap / nmap / dirsearch / gobuster / ffuf / acunetix / xray / 御剑 等 30+ 工具指纹 |
| HTTP-METHOD | 非常规方法 | 中 | PUT / DELETE / TRACE / PROPFIND / MOVE / COPY |
| UA-SUSPICIOUS | 可疑 UA | 低 | UA 为空或过短、python-requests / curl / java 等脚本客户端（误报多，仅供参考） |

## 五、行为判定（不靠关键字，靠行为特征）

单条关键字很容易被绕过，所以扫描器和 Webshell 用**行为**来判定：

| 行为 | 判定条件 | 为什么这么定 |
|---|---|---|
| 疑似目录扫描 | 请求数 ≥ 40 **且** 404 比例 ≥ 55% **且** 不同 URI 数 ≥ 25 | 真实扫描器的特征是"打很多不同路径、大量 404"，单看某一条请求看不出来 |
| 疑似 Webshell 交互 | 同一 URI 被同一 IP **POST** ≥ 8 次 | 正常页面不会反复 POST 同一个脚本文件，这是菜刀/蚁剑类工具的典型交互 |
| ⚠ 可能利用成功 | 命中 critical 级规则 **且** 返回 2xx | 404/403 说明没打通，返回 200 才是最需要立刻确认的情况 |

## 六、优先级打分

```
分数 = Σ(命中规则的级别权重)          # 同一规则只算一次，防止刷量刷分
     + 15（疑似目录扫描）
     + 20（疑似 Webshell 交互）
上限 100
级别权重：严重 40 / 高 18 / 中 7 / 低 2
```

**为什么同一规则只算一次**：如果按命中行数累加，一个有 5000 条 SQL 注入尝试的 IP 会把分数刷满，而一个只尝试了 1 次命令执行但**打成功了**的 IP 反而排到后面。安全运营要优先看的是"可能已经进来的"，不是"叫得最响的"。

## 七、输出示例

```
【攻击类型分布】
级别   | 攻击类型          | 涉及 IP 数
-------+-------------------+-----------
[严重] | 命令注入          | 1
[高]   | 扫描器 User-Agent | 3

【需优先研判的源 IP（按优先级排序）】
分数 | 级别   | 源 IP         | 命中行 | 总请求 | 命中类型
-----+--------+---------------+--------+--------+--------------------------
80   | [严重] | 198.51.100.11 | 2      | 2      | 命令注入、路径穿越
69   | [高]   | 198.51.100.21 | 82     | 82     | 扫描器 UA、敏感路径探测
38   | [高]   | 198.51.100.33 | 14     | 14     | 文件上传/脚本落地

--- 198.51.100.33  分数 38 ---
    行为判定: 疑似 Webshell 交互(/uploads/2026/x.jsp)
    · POST /uploads/2026/x.jsp  规则 文件上传/脚本落地  HTTP 200
```

导出物：`report.json`（结构化全量报告）、`hits.csv`（可直接贴进值守日报的明细表，UTF-8 BOM，Excel 打开不乱码）。

## 八、几个设计取舍（面试可以主动讲，显工程素养）

1. **为什么规则是数据而不是 if-else**：`RULES` 是一张表，加一类攻击只改表不改逻辑。真实运营里攻击手法每周都在变，工具必须能快速迭代。
2. **为什么先 URL 解码 3 次再匹配**：攻击者常用双重编码（`%2527` → `%27` → `'`）绕过关键字检测。不解码，规则形同虚设。
3. **为什么要统计"解析失败行数"**：日志里可能有换行、裸引号、非标准格式。**解析失败被静默吞掉是安全工具最危险的缺陷**——你以为看全了，其实漏了一截。所以宁可报出来让人看。
4. **为什么支持白名单**：真实环境里最大的误报来源不是攻击者，是**自家的漏扫和内网资产**。不排掉它们，运营人员每天第一件事就是处理自己人。
5. **为什么退出码在有严重级命中时返回 1**：这样可以直接接进 CRON / CI / SOAR，实现"发现严重级攻击自动告警"。
6. **为什么零依赖**：护网现场往往在内网、无法联网装包。能拷过去就跑，比功能多更重要。

## 九、已知局限（**主动说局限，比被问出来强 10 倍**）

1. **URL 日志看不到请求体**——所以文件上传、POST 型 SQL 注入、Webshell 命令内容都检测不到。真实环境必须配合 WAF 日志或全流量设备（这正是蓝队"设备联动"的意义）。
2. **规则匹配必然存在误报**——业务参数里出现 `select`/`union` 等词会被误伤，所以工具定位是"筛查"不是"定性"，最终必须人工复核。
3. **阈值是经验值**——`40 次请求 / 55% 的 404 比例` 是按中等规模站点估的，真实环境要按业务流量基线调，否则小站点会全是扫描、大站点会全是漏报。
4. **没有威胁情报联动**——目前只判断"行为像不像攻击"，不能判断"这个 IP 是不是已知恶意 IP"。
5. **一次性读入内存**——GB 级日志会有内存压力，应该改成流式逐行处理。

## 十、后续可以怎么改进（面试官爱问"这个项目还能怎么升级"）

- **威胁情报联动**：接微步 / 奇安信 / VirusTotal API，对源 IP 做信誉查询，把"行为可疑"升级成"行为可疑 + 情报命中"
- **ATT&CK 映射**：把每类规则映射到 MITRE ATT&CK 战术（初始访问 / 执行 / 命令与控制 / 数据外传），报告直接按战术阶段输出——这才是蓝队报告的标准语言
- **误报反馈闭环**：记录运营人员"确认误报"的操作，自动学习生成白名单，减少重复劳动
- **GeoIP 画像**：标注源 IP 归属地和 ASN，境外 IP 攻击可以直接提升优先级
- **流式处理 + 支持 JSON 日志**：对接 ELK / 天眼导出的 JSON 格式，改成 `for line in fh` 流式读，支持 GB 级日志
- **输出 STIX 2.1**：把 IOC 以标准格式输出，可以直接导入态势感知平台
